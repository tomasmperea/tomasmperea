# Auditoría VAL-74 — el tope de la capa de IA lo pone la base, no una suposición

**Commit auditado:** `831ba3e4bcfc89c4fcae3c619ec9e55a67275ba2` · **Árbol:** limpio (`git status --porcelain` vacío,
verificado antes y después de auditar) · **Publicado:** no (VALIJA_VERSION 22→23, artifact todavía sirve una
versión anterior; no se intentó publicar nada durante esta auditoría).

## Veredicto: NO PUBLICAR — 38/100

No llega ni al piso de "candidato" (70). Y no es por el teléfono: es porque el mecanismo central de esta
entrega — el cálculo del cupo — tiene un defecto reproducible en Node, en menos de diez minutos, con un
insumo perfectamente realista. El propio encargo de auditoría lo señalaba como el riesgo a cazar; lo cacé.

## El hallazgo central, primero

`cupoDeItemsIA` (`app/parts/packing-engine.js:227-243`, idéntico en `app/valija.html`) estima cuántos ítems
más entran en el documento de 256 KiB dividiendo el tamaño actual de la lista por su cantidad de ítems, y
asume que cada ítem nuevo va a pesar lo mismo que el promedio de los viejos:

```js
function cupoDeItemsIA(list) {
  var actual = 0;
  try { actual = JSON.stringify(list || {}).length; } catch (e) { actual = 0; }
  var n = itemsArray(list || {}).length || 1;
  var porItem = Math.max(200, Math.ceil(actual / n));
  var libre = TOPE_LISTA_BYTES - MARGEN_LISTA_BYTES - actual;
  return Math.max(1, Math.floor(libre / porItem));
}
```

Reproduje esto extrayendo el motor de `app/valija.html` (misma técnica que `motores-desde-html.js`) y
construyendo la lista base real de un viaje a Noruega (28 ítems, igual que la que cita el commit):

```
cupo calculado sobre la lista base: 561        (coincide con el commit)
motivo realista, una frase con acentos: 284 caracteres / 293 bytes UTF-8
enrichWithDestination con 561 ítems, todos con ese motivo:
  tamaño final (char length):      372.490
  tamaño final (UTF-8 bytes reales): 378.700   de un tope de 262.144
  ¿se pasó del tope?  SÍ — un 44% arriba
```

Script y salida completa: `/tmp/claude-0/.../scratchpad/val74-worst-case.js` (reproducible con
`node app/pruebas/...` extrayendo el motor igual que `val74-sin-tope-de-ocho.js`; puedo repetirlo si hace
falta el archivo en el repo). Esto **no es un caso extremo**: es una sola frase de motivo, del largo que el
propio prompt le pide al modelo ("por qué, en una frase, mencionando el dato del destino"), aplicada a un
lote de tamaño que el propio cupo calculó como "seguro". El resultado es un documento que la base rechaza
(`invalid_argument`, "documento de más de 256 KiB se rechaza" — contrato citado en
`docs/briefs/adjuntar.md:315` y `docs/arquitectura.md`).

**Por qué el cupo se equivoca, dos causas independientes, las dos verificadas:**

1. **Mide en caracteres, no en bytes.** `JSON.stringify(list).length` cuenta unidades UTF-16 de JS, no bytes
   UTF-8. El propio `app/valija.html` ya tiene la forma correcta de medir esto —`bytesDeTexto()`,
   `bytesSerializados()`, con el comentario explícito **"Se MIDE, no se estima: es la única forma de saber si
   un cuerpo pasa los 256 KiB"** (línea 5586-5593)— y `cupoDeItemsIA` no la usa. Para texto en español con
   acentos (que es literalmente todo el vocabulario de esta app) el error es chico por carácter pero
   sistemático.
2. **Estima el costo del ítem nuevo a partir del promedio de los ítems viejos**, que son las reglas base
   (motivos cortos, 20-90 caracteres, ver `packing-engine.js:656-849`). El ítem nuevo lo escribe un modelo al
   que el prompt le pide justamente lo contrario de "corto": "citá el dato concreto ... 'tu escala en Lima es
   de ocho horas', no una generalidad". No hay ningún tope de longitud en `nombre` ni en `motivo` — a
   diferencia de `sanitizeNotesForAI` (recorta a 240) o el título de reservas (recorta a 80, línea 1476), que
   sí se defienden. Un ítem de la IA puede pesar lo que quiera.

El comentario de `MARGEN_LISTA_BYTES` dice literalmente **"para que un ítem largo no quede justo en el
borde"** — comprobé que un solo motivo de ~1,6 KB ya empieza a competir con ese margen de 8 KB, y con 561
ítems de motivo normal (no extremo) el margen es irrelevante: se pasa por 116 KB. El comentario promete algo
que el código no cumple.

También dice **"Mismo criterio que el de los adjuntos"**. Comprobé que no lo es: el margen de adjuntos
(`TOPE_ARCHIVO_BYTES`, `adjuntos-engine.js:117-119`) es una cuenta **exacta** sobre la expansión conocida de
base64 de UN archivo de tamaño conocido antes de subirlo. El margen de packing es un colchón fijo sobre una
**estimación** de N ítems de tamaño desconocido. Comparten el número 8192 y el propósito declarado, no el
método — la analogía sobregira la confianza que merece el número.

## El piso de 1 (punto 2 del encargo)

`Math.max(1, ...)` nunca deja pasar cero, sin importar cuán negativo sea `libre`. Construí una lista a 261,7
KB (un estado alcanzable: cualquier doc bajo 262.144 se guarda) y until pedí un solo ítem con un motivo de
12.000 caracteres (`"Palabra ".repeat(1500)"`, nada exótico, un modelo suelto puede devolver un párrafo así):
el documento final quedó en 274.142 bytes, **12 KB arriba del tope**. Guardado va a fallar.

**Y el mensaje que ve la persona en ese fallo no sirve — lo verifiqué leyendo `writeErr` (`app/valija.html:8131`):**

```js
function writeErr(e){
  if(e && e.code === "invalid_argument") return "Tenés acceso de sólo lectura a esta valija";
  if(e && e.code === "quota_exceeded") return "La valija llegó a su límite de reservas";
  return "Guardado en este dispositivo. No se pudo sincronizar todavía";
}
```

El contrato de la base dice que un documento de más de 256 KiB se rechaza con `invalid_argument`
(`docs/briefs/adjuntar.md:315`). Ese código, en esta ruta, se traduce como **"Tenés acceso de sólo lectura a
esta valija"** — una causa inventada y falsa: la persona no perdió permisos, un motivo de la IA infló el
documento. Confirmé además que este error llega por `Store.onSyncError` (`app/valija.html:11177`,
`Store.onSyncError = e => toast(writeErr(e), true)`), no por el `try/catch` local de `runGenerate`, porque
`Store.savePacking` no espera la escritura real (la dispara con `this.sync(...)` sin devolver la promesa) —
así que ese `catch` de `runGenerate` no va a atrapar este fallo en la práctica; es una falsa red de seguridad.
El comentario de `cupoDeItemsIA` dice *"si la lista ya está en el límite, el problema es otro y se ve en el
guardado, no acá"* — comprobé qué se ve, y es un mensaje que **inventa una causa**, exactamente lo que
`CLAUDE.md` nombra como regla no negociable ("El mensaje de error no inventa una causa").

Antes de VAL-74 este camino era casi imposible de alcanzar: con `MAX_AI_ITEMS = 8` y motivos cortos, la IA
nunca acercaba la lista a 256 KiB. Esta entrega, al sacar ese tope, **abre la exposición a un bug ya existente
en `writeErr`** y no lo prueba ni lo declara.

## Punto 3 — el arnés `val74-sin-tope-de-ocho.js`

Corrí el arnés: **17/17 aserciones en verde**, coincide con lo reportado. La extracción del motor es fiel —
la comparé byte a byte contra `app/parts/packing-engine.js` (ver punto 4) y usa la misma técnica que
`motores-desde-html.js`. El control final (recortar a 8 y comprobar que entran 8, no 25) es real y sirve: si
el cupo volviera a ser 8, esa aserción rompe.

Pero el arnés **no prueba lo que el propio encargo pedía cazar**:

- Línea 96: `const bytes = JSON.stringify(tapada).length;` — mismo error de medición que la producción (chars,
  no bytes UTF-8). Como el texto de prueba es ASCII puro (`"Item " + k`, sin acentos), esta medición
  incorrecta no se nota — el arnés tiene el mismo punto ciego que el código que audita, así que no puede
  descubrir el defecto. Es la misma familia de error que "el simulador escrito de memoria": en vez de leer
  el contrato ya establecido en el propio archivo (`bytesDeTexto`), reimplementa una medición inexacta.
- Los motivos de la prueba de 2.000 ítems son cortos y parejos ("motivo largo para ocupar lugar numero N" +
  40 espacios) — un tamaño cercano al promedio histórico que `cupoDeItemsIA` ya asume, no el caso "motivos
  largos" que el propio encargo pedía cazar. Por eso el arnés da 207.440 caracteres de 262.144 y "todo bien":
  nunca ejercitó el escenario que rompe el cálculo.
- Ninguna aserción del arnés construye una lista cerca del tope para ejercitar el piso de 1.

No encontré ninguna aserción que pase por un motivo distinto del que dice — las que hay miden lo que afirman
medir. El problema no es que mientan: es que no preguntan lo que había que preguntar.

## Punto 5 — el prompt

`"Agregá los ítems que hagan falta, sin llenar por llenar"` reemplaza a `"Agregá hasta 8 ítems"`. Leí el
resto del prompt (`destinationPrompt`, `packing-engine.js:1521-1560`): las "Reglas que no se rompen" (no
inventar, omitir si no hay certeza, devolver vacío si no hay nada seguro) siguen intactas y son un freno real
sobre la certeza del contenido — pero **ninguna frena la longitud ni la cantidad**. "Sin llenar por llenar"
es una instrucción de estilo, no una restricción estructural: nada en el parser la hace cumplir. Es
razonable como intención de producto, pero es exactamente el tipo de instrucción que un modelo suelto puede
ignorar parcialmente sin que nada del código lo note — y es además la entrada que alimenta el defecto del
punto 1 si el modelo decide escribir motivos más largos de los que hoy escriben las reglas base.

## Punto 6 — lo que no se midió

Confirmé que el criterio de aceptación **escrito en el propio `docs/backlog.md` (líneas 526-528, antes de la
resolución)** decía: *"Antes de elegir un número nuevo se mide: cuántos ítems propone el modelo sin tope ...
con `app/pruebas/lote-modelo-real.js`"*. La sección "CONSTRUIDA" (líneas 533-548) no lo menciona, ni para
cumplirlo ni para declarar por qué se omite. Es cierto que el PM redefinió el problema ("no tiene por qué
tener un tope real") y que por eso no hay "un número" que medir de la misma forma — pero eso no vuelve
irrelevante la pregunta de calidad que la propia historia planteaba: sin tope, ¿cuánto y qué tan largo
responde un modelo real? Esa pregunta sigue sin contestar, y **no está escrita como pendiente en ningún lugar
del commit ni del backlog** — sólo la mencionó quien entregó cuando se le preguntó directamente en el encargo
de esta auditoría. Eso es "queda en la cabeza", no "queda en la entrega", que es exactamente lo que
`CLAUDE.md` prohíbe. Sí es una brecha que hay que declarar en el guion del PM, y hoy no está declarada en
ningún artefacto del repo.

## Lo que falta para llegar a 85, en orden

1. **Cambiar `cupoDeItemsIA` de estimar a medir**, igual que ya hace `bytesSerializados`/`bytesDeTexto` para
   los adjuntos: acumular ítems candidatos uno por uno y cortar cuando el tamaño real (UTF-8, medido, no
   `JSON.stringify(...).length`) del documento completo supere `TOPE_LISTA_BYTES - margen`, no cuando se
   agote un conteo calculado de antemano por promedio. Esto elimina las dos causas a la vez (caracteres vs.
   bytes, y promedio vs. ítem real) porque deja de depender de un promedio.
2. **Poner un tope de longitud a `nombre` y `motivo` de los ítems que vienen de la IA**, con el mismo criterio
   que ya existe para notas (240) y títulos (80) en el mismo archivo. Aunque se arregle el punto 1, un
   motivo sin límite sigue siendo una superficie de riesgo abierta.
3. **Corregir el mensaje de `writeErr` para `invalid_argument`** en el contexto de guardado de la valija (hoy
   dice "acceso de sólo lectura", que es falso cuando la causa real es tamaño de documento) — o, como mínimo,
   verificar y declarar qué mensaje ve la persona hoy en este camino específico, en vez de asumir que "se ve
   en el guardado" alcanza.
4. **Probar el caso de motivos largos y el caso de lista casi llena** en `val74-sin-tope-de-ocho.js`, midiendo
   en bytes UTF-8 reales (no `.length`), antes de dar el arnés por representativo del riesgo que el propio
   ticket señala.
5. **Escribir en el backlog, como pendiente explícito**, que no se midió con un modelo real cuántos ítems ni
   de qué largo devuelve bajo el prompt nuevo, y qué se va a mirar en el guion del PM para saberlo (por
   ejemplo, contar ítems y caracteres de motivo en el primer ajuste por destino real que haga el PM).
6. **Corregir el comentario de `cupoDeItemsIA`** (580 ítems / setenta y dos veces) para que coincida con el
   número real (561 / setenta veces) que el propio commit reporta, y ajustar "mismo criterio que el de los
   adjuntos" para que no sugiera un rigor que el mecanismo actual no tiene.

## Lo que nadie puede verificar desde acá

Esta sección no queda vacía: hay dos cosas reales que sólo se comprueban con el PM.

1. **Qué tan largos y cuántos son los ítems que devuelve el modelo del visor del teléfono del PM**, con el
   prompt nuevo, sin el freno de "hasta 8". `lote-modelo-real.js` prueba con OTRO modelo (el que responde
   desde este entorno), no el que usa `claude.use("sample")` en el teléfono del PM — puede comportarse
   distinto en longitud y en cuántos ítems arriesga con "sin llenar por llenar" en vez de un número. Pasos
   para comprobarlo: publicar, entrar a un viaje con reservas cargadas, tocar "Armar la lista" o "Rehacer la
   lista", y con la consola del dispositivo correr `ValijaTier.resumen()` — no da longitud de motivo, así que
   además convendría, antes de publicar, agregar una línea de registro con la cantidad de ítems y el largo
   total de motivo del último ajuste por destino (mismo espíritu que el "sello de versión" que ya usa la app
   para otros defectos que sólo aparecen en el teléfono).
2. **Si el escenario de sobrepaso que reproduje en Node (documento un 44% arriba del tope) es realmente
   alcanzable con el modelo del teléfono**, y si en ese caso la persona efectivamente ve "Tenés acceso de
   sólo lectura a esta valija" en pantalla. Esto se puede forzar sin esperar a que el modelo real lo genere
   solo: cargar a mano, desde la consola del navegador del Artifact publicado (no hace falta el teléfono para
   esta parte, pero si se quiere confirmar el mensaje tal como lo ve el PM, sí), una lista con ~560 ítems de
   motivo largo vía `Store.savePacking` y mirar qué toast aparece.
